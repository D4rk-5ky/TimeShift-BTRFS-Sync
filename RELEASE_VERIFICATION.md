# Release verification — TimeShift-BTRFS-Sync 0.2.6

Prepared 2026-11-13 from source 0.2.5. Increment by exactly 0.0.1; retain all prior VERSIONING entries and the patch-99 rollover policy. Compare against source 0.2.5 and the supplied TimeShift-BTRFS-Sync-main.zip (source 0.2.2).

## Current behavior and changes

- Add cleanup counts and a cleanup progress bar to the existing manufacturer-selected HA Markdown card. Show confirmed/current expected date jobs, evaluated/blocked jobs, current cleanup group/date/item number, initial expectation and current expectation. Retain the first known expectation when later plans change.
- Initial cleanup expectations are explicitly provisional. At the existing initial sync queue checkpoint and later queue refreshes, reuse the pure retention/source-app plans and the existing redundant-date selectors against a disposable state projection including future queued sends and current source tags/comments. Add no inventory commands, send-size probe, state write, deletion authorization or destructive operation to forecasting. Optional forecast failure becomes unknown.
- At real cleanup start, existing reconciliation and source/destination checks refresh paired/source-only candidates. Each extra cache/destination stage replaces its estimate after its existing fresh inventory and verified-window checks. Disabled/not-applicable stages have an empty plan; unavailable required inventory/window remains unknown. Totals can grow or shrink without losing completed history.
- Count one cleanup date workflow per job. A paired retention date requires all configured destination, optional send-cache and app-created source Timeshift actions plus state removal; it is not complete merely because one side succeeded. A legacy source-only, redundant cache-only or redundant destination-only date is its own job. Individual Btrfs child subvolumes and containers are not separate progress units. Existing CLI per-side deletion summaries retain their detailed counts.
- Blocked/refused or failed work advances evaluated counts only, remains unconfirmed/pending and cannot complete its progress bar. Unknown inventories and unverified forecasts do not become fabricated zeros or successful cleanup. On a normal return, unfinished/unverified cleanup yields monitor status incomplete and cannot replace retained last success. Existing CLI return codes and legacy completion-message behavior are unchanged.
- Add overall expected/completed/remaining step counts and a combined bar: one complete transferred date or one confirmed cleanup date job is one equally weighted step. It is not byte progress or estimated remaining time. Unknown component totals keep overall total unknown. Completed work survives replanning; added work can decrease the percentage. No-op is 0/0 without an invented percentage; displayed percentages are rounded down so unfinished work cannot round to 100%.
- Optional standalone real prune now uses the same live monitor while holding the existing job flock, with operation=prune, zero transfer dates, whole-CLI runtime and duplicate-run event isolation. Sync/prune of one config share its device, current/latest-result and latest successful monitored-operation history. Dry-run prune remains outside live monitoring/locking/state writes; standalone prune still cannot delete redundant-only extras without successful sync in this invocation.
- Existing status/result attributes carry all new counters and per-group breakdowns through the same fourteen discovery sensors. Manufacturer remains the only card selector. Earlier compatible scripts lacking cleanup/overall metrics still render their existing data. Actual streamed-byte measurement, whole-run speed/runtime, role-based entity discovery, retained/live ordering and independent last-success retention remain intact.
- Update current README/INSTALL, all eight complete config examples, prune descriptive help, config audit, full code maps and both version ledgers. Preserve supplied disclaimers and every original/prior file. No dependency, command, flag or configuration option is added; all parsed config option values are preserved.

## Limits and supplied executable

No live HA frontend/device-registry update, MQTT broker/socket delivery, SMTP delivery, real Btrfs snapshot/send/receive/deletion, Timeshift scheduler/retention, SSH/sudo endpoint, restored boot or deployed systemd execution was tested. Forecasts intentionally depend on the last available in-memory inventory and predicted successful sends; only the existing real cleanup proofs authorize actions. Changes are noticed at existing source refreshes, cleanup start and fresh extra-stage inventories, not by continuously polling storage during every individual deletion. A newly changed extra candidate can still be blocked by the existing immediate pre-delete checks. Optional live delivery remains best effort.

Python 3.11–3.13, complete dependency installation and PyInstaller builds remain untested. The original dist/ts-btrfs/ts-btrfs is preserved byte-for-byte but still cannot start because the supplied ZIP omitted its required _internal runtime including libpython3.14.so.1.0. Its originally documented 0.1.84 version cannot be verified. Use/install the verified 0.2.6 Python source or rebuild with PyInstaller, which is unavailable here.
